# Benchmark record conventions

## Schema versions

Each record identifies its type and schema version. Update the schema version when required fields or their meanings change. Tasks and hidden instances also carry content versions so records can reference a specific definition.

## Public tasks and hidden instances

A public task defines its ID, version, family, goal, protocol/context, observed failure, permitted actions, and diagnostic-action budget. Optional assumptions describe its scope. Keep `instruction.md` consistent with the task record.

An optional `required_output` object lists agent-authored per-round and final fields. `environment_output` lists the environment-populated round fields. `hypothesis_format` identifies the ranked representation, a count of three, and agent-generated hypotheses. Public tasks supply context and actions; candidate hypotheses are generated by the agent. A null diagnostic-action limit records an unresolved authoring value; repository validation flags it before interaction can begin.

Store ground truth, simulator definitions, curator sources, and split assignments outside public task records. Hidden instances reference a task/version and contain a diagnosis, hidden-state IDs, a simulator reference, scenario group, split, provenance references, and curation metadata.

`split` is `development`, `validation`, or `test`. Related variants share a `scenario_group_id` and split. Curation metadata records status, reviewer, date, and notes. Approved records require a reviewer and review date.

`hidden_instances.json` can group individual instance records under an `instances` array. Each member follows the existing hidden-instance schema.

## Interface declarations

`bioloopbench/interfaces.py` declares Python protocols:

- `Environment.start()` returns public task context and remaining budget.
- `Environment.step(action)` returns an observation and remaining budget.
- `Simulator.transition(hidden_state, action)` returns the next hidden state and a public observation on the private side.

Task-specific definitions specify response behavior, prerequisites, repeat behavior, stochasticity, and material changes. The budget field counts diagnostic actions. `simulator.kind` identifies a lookup or state-machine definition; `unspecified` and a null reference are available during authoring.

Deterministic lookup records live in `simulator/private/`. They map hidden-state and action IDs to observation text and are referenced by `simulator_id`. The trusted `observation_for` helper returns that text as `content`, with an environment-assigned `observation_id` and `source: environment`. An evaluated agent receives public task files and selected observations through a restricted interface; it must not be given repository access to private records or the lookup object. Environment rules belong under `environment/`; evaluator references belong under `evaluation/private/`.

## Trajectories

A trajectory links a run ID, task/version, and optional instance ID. Each round contains exactly three ranked hypotheses before and after feedback, the selected action, an observation, a revision summary, cited evidence IDs, and remaining budget. The final record contains a diagnosis and evidence IDs.

The trajectory combines fields from two owners:

| Fields | Populated by |
|---|---|
| `hypotheses_before`, `action` | Agent, before the diagnostic result |
| `observation`, `remaining_budget`, `round_index` | Environment/simulator and trusted logger |
| `hypotheses_after`, `revision_summary`, `evidence_ids` | Agent, after receiving the result |
| Final `diagnosis`, `evidence_ids`, `explanation` | Agent |

The agent requests an action and waits. The environment obtains its result for the active hidden instance, records it, and supplies feedback. The agent then revises its hypotheses. The initial `observed_failure` is benchmark-supplied task context.

Observation records require `source: environment`. Schema annotations identify each round field's owner and mark observations read-only. Agent submission schemas exclude environment fields. `make_round` in `bioloopbench/trajectory.py` assembles the log from separate validated submissions and trusted feedback; the model does not submit a complete trajectory round. The source marker records attribution, while the trusted environment boundary determines where the data actually originates.

The controller accepts `act`, `update`, `finish`, and `abort` JSON messages. It enforces submission order and diagnostic budgets and saves trajectories after accepted messages. While awaiting an update, the action, hypotheses, observation, and remaining budget are preserved in optional `pending_round`. Completed trajectories require a final diagnosis and no pending round. Aborted trajectories can retain pending feedback.

The final record also supports an `explanation` string. A task can require it in `required_output.final_fields` to request a concise explanation linking observations to the diagnosis.

`draft` permits an empty log and null final record. `completed` requires a final record. `aborted` preserves a partial log.

Each hypothesis contains `hypothesis_id`, `description`, and integer `rank`. Both lists contain exactly three distinct entries, ordered at ranks 1, 2, and 3. Rank 1 is most likely, rank 2 second most likely, and rank 3 third most likely. The schema rejects tied, missing, out-of-range, and out-of-order ranks, as well as confidence fields. The validator also rejects duplicate IDs and repeated descriptions within a list.

The agent generates descriptions from the visible context and observations, re-ranking the same or revised set after each result. Keep an ID for a continuing hypothesis even when its rank changes; assign a new ID for a different explanation. Record revisions and replacements in `revision_summary`. Evidence can justify unchanged rankings. The final diagnosis should reflect the latest rank-1 hypothesis.

The observed failure has reserved evidence ID `initial_failure`. Subsequent observation IDs are unique. Evidence citations refer to initial evidence or observations already received. Round indices begin at one and are contiguous. Repository validation checks action IDs and remaining budget against the linked task.

Store trajectories on the evaluator side and expose only the information required by the interaction interface.

## Provenance and leakage controls

Provenance records contain source IDs, titles, and URLs. Construction notes distinguish source-supported relationships from authored scenario content.

Sources may also record authors, year, and DOI. A null URL indicates that a source link has not been recorded. Private `action_evidence` records hold interpretations, strengths, supporting source IDs, and caveats; public actions and returned observations exclude these annotations.

Leakage-control fields describe synthetic construction, source use, lookup policy, and checks with planned/passed/failed status. Null and unspecified values identify incomplete authoring fields. Keep related variants and counterfactual siblings in the same scenario group and split.

## Evaluation

`evaluation/metrics.json` lists metric names and descriptions. Recovery@K measures correct diagnosis within K diagnostic actions. Evaluation definitions specify K values, denominators, rank-revision and anchoring rubrics, ambiguity handling, and aggregation rules.

Rank-based evaluation can track the correct hidden cause moving upward after supporting evidence, contradicted hypotheses moving downward, and persistence of an earlier incorrect top-ranked hypothesis. Match agent-generated explanations to hidden causes on the evaluator side without disclosing candidates. A cause absent from the three hypotheses is recorded as not listed, rather than assigned an invented rank.

Feedback conditions include true, absent, and shuffled/counterfactual feedback.

## Validation coverage

The validator uses JSON Schema Draft 2020-12 with local schema resolution. It checks record structure, IDs, evidence chronology, and log consistency. Individual paths validate records independently. `--repo` adds task/version/provenance/simulator references, split grouping, action coverage, budgets, and public/private placement checks. It includes records under `simulator/private/`. The default command checks the template bundle.

Scientific review covers biological realism, simulator behavior, solvability, difficulty, source quality, and diagnosis interpretation. Lookup validation checks structural completeness; it does not establish biological validity or the sufficiency of diagnostic evidence.
